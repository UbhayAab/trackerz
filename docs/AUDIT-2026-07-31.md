# Full audit - 2026-07-31

Everything below was measured against the live database and the deployed
functions, not read off the code. Numbers are as of 2026-07-31 06:00 IST.

## 1. The APK could never install - FIXED

Root cause, confirmed by extracting the signer certificate from two published
builds six minutes apart:

```
run 30153825634  d8f0df6e68f854bc4ba98b834948569d486dc43ce8032fdb8e34dcea9384df40
run 30154001974  0078982d0160ca433f179c0385f85117e7796c8ca7ee1a25c8ef8c234220e7bc
```

`assembleDebug` with no keystore makes the Android Gradle Plugin generate a
fresh random `~/.android/debug.keystore`. GitHub runners are ephemeral, so
**every single build was signed by a different key**. Android identifies an
installed app by (applicationId, signing certificate), so the newer APK could
not install over the older one - "App not installed", no explanation.
`versionCode` was also pinned at 1 forever, which independently lets the
installer refuse an upgrade.

Fixed: one keystore from the `ANDROID_KEYSTORE_B64` repo secret (the repo is
public, so it is a secret and gitignored, never committed), release-signed with
v2+v3, `versionCode` from the CI run number, and an `apksigner` step that fails
the build if the fingerprint ever drifts. A build without the secret still
compiles but is refused publication to the permanent link.

Verified across two consecutive published builds:

```
build 20  d4e36fdc74b185d1012dc1b18ad3e5d30fb15d458db288127a9f6c5d04186a1a
build 22  d4e36fdc74b185d1012dc1b18ad3e5d30fb15d458db288127a9f6c5d04186a1a
```

**One-time action on the phone:** uninstall any Trackerz built before
2026-07-31 before installing this one. Those were each signed with a different
throwaway key, so Android will refuse to replace them. After this build,
updates install normally.

Still unverified: whether OnePlus OHealth actually populates Health Connect on
this OxygenOS build, and whether Play Protect objects to the `READ_SMS` +
notification-listener combination on a sideloaded app. Both need the phone.

## 2. Every note in the database was a misfile - FIXED

All 8 rows in `notes`, audited against the domain row from the same ingestion:

| When (IST) | Body | Domain row from same capture | Verdict |

| 07-01 10:22 | Did not go to gym today | none | orphan - the skip was never recorded |

| 07-28 06:29 | Coca Cola Zero... (order manifest) | food_log | double-write |

The mechanism, straight from `ai_actions`:

```
07-23 05:26:18  create_note_candidate         {"body":"In gym, doing back, will do let press too"}
07-23 05:26:19  create_workout_log_candidate  {"status":"done", ...same text..., _auto_expanded:true}
```

The model emitted only a note. Deterministic salvage correctly synthesized the
workout. **Nothing dropped the note.** One training session, two tables.

Fixed in `dropRestatingNotes` (`lib/fan-out-expander.mjs` + edge mirror): a note
whose body restates the capture that already produced a domain row is dropped.
The test is coverage of the evidence, not novelty in the note, so a mixed
capture ("ate 6 eggs, also cancel the trainer") keeps its remainder.

The 8 rows were cleared on the owner's approval by
`scripts/repair-notes-2026-07-31.mjs`: 5 restating notes deleted (the domain row
from the same capture already holds the event), 2 contradicted 23 July notes
deleted (he trained that morning), and the 07-01 orphan converted into the
`workout_logs status='skipped'` row it should always have been. Every action is
in `audit_log`. `notes` is now empty and no event was lost.

## 4. The AI could only ever write - FIXED

A question routed to `request_user_review` tagged "query". That queue has never
been rendered in any surface. Four rows, all still `proposed`. So asking the app
anything produced silence.

Now `answer_question`: a non-write tool rendered as a card above the capture
box. Teaching the main prompt to answer was not enough - measured against the
deployed function, a question came back with an empty `tool_calls` array about a
third of the time. A question the main pass leaves unanswered now gets one
dedicated single-purpose call. Verified over three consecutive live runs, 9/9:

- "How much have I spent this week?" -> "Rs 449 across 2 transactions" (correct)
- "Am I on track with my protein?" -> "roughly 81g/day against your 162g target"
- "How many steps did I do yesterday?" -> "I do not have your step data"

Two defects this exposed and fixed:

- The context block fed the model **gross outflow** as "spent". Since the
  statement import the ledger also holds card bills, SIPs and self-transfers -
  77% of outflow over the two real statements. Now `rowCountsAsSpending`.
- The **enforced daily target was absent** from the context, so the model
  answered "I don't have your protein target" while every gauge rendered 162g
  (it comes from the diet scaffold, not a saved budget row).

## 8. Food quantities were being silently dropped

`curd` is `kind: "count"` with a katori serving and carried no `gramsPerUnit`,
so `multiplier()` fell back to ONE serving whatever quantity was stated. Because
the table's totals OVERRIDE the model when `recognized` is true, that fallback
won. On the real 2026-07-25 row:

```
"6 boiled eggs and 500ml curd"  ->  522 kcal / 42.8g protein
```

That is 6 eggs plus a single 150g katori - half a litre of curd charged as one
small bowl, costing ~12g of protein on the exact metric he is short on. 63 of
the 65 count-kind foods had the same gap.

Fixed two ways: serving sizes added for the 24 foods actually logged by weight
or volume (katori 150g, bowl 250g, glass 250ml, cup 150ml), and where the table
still cannot convert a stated quantity it now reports it in `unscaled` and drops
`recognized` to false, so the model prices it rather than the table asserting a
serving count nobody stated. The 100x guard ("250 g rice" must not become 250
katoris) is unchanged and locked by test.

`blueberry` was also missing entirely despite appearing in 3 captures.

`tests/food-mirror.test.mjs` now compares `recognized`, `unscaled` and every
`gramsPerUnit`/`mlPerUnit` between lib and the edge copy, not just macros -
verified to fail on injected drift.


## 9. Reporting a missed session rewrote the plan you missed

Found by running a real capture through the deployed pipeline:

```
"drakn 500 g curd, with 2 scoops of protien powder. and no gym today"
  -> create_food_log_candidate     conf 0.95   (correct)
  -> create_workout_log_candidate  conf 0.90   status=skipped  (correct)
  -> update_plan_candidate         conf 0.55   replace today's Workout B with Rest
```

All three auto-applied, because there is no review gate. The last one made
`workout_logs` and `user_plans` disagree about the same day: the log says a
session was skipped, the plan says the day was always rest. `jbPlannedWorkout`
reads the plan, so the miss became `workout_forgiven`, the evening nudge went
quiet, and the next morning's brief would have called it a rest day.

The effect compounds: **every miss you honestly report launders itself into a
planned rest day**, so the gym consistency numbers stop measuring anything. It
had happened before - `user_plans` also holds "No gym due to travel and rest"
from 2026-07-05.

Fixed in `isSameDayGymPlanChange` (lib + edge mirror): a bare denial cannot
produce a gym plan change scoped to that one day. A multi-day scope survives,
because "going to Nagpur tomorrow and the day after, no gym today" really is
about days that have not happened yet, and an explicit instruction ("change my
gym today to rest") is routed as `plan_change` and never treated as a denial.

Also fixed: the skipped row was taking the WHOLE capture as its description, so
the Gym log read "drakn 500 g curd, with 2 scoops of protien powder. and no gym
today". It now takes only the clause that carries the denial.

`scripts/capture.mjs` was added to make this kind of check routine - it runs a
real sentence through the deployed pipeline and prints every row that landed,
with `--dry` for local-only and `--undo <id>` to remove everything a capture
wrote.
